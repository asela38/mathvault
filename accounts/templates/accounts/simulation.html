How the compromised-password check works

In production the filter is built once a month from the full Have I Been Pwned corpus (about 1.9 billion SHA-1 hashes, a 4.3 GB file). This page runs the same code (accounts/pwned/bloom.py and BloomPwnedValidator) on a list small enough to watch. Two stages: 1. build the bit array from a password list, 2. check a candidate password against it.

Stage 1 — build the filter from a password list

Sizing

The same formula sized the production file: n = 1.9 × 10⁹, p = 10⁻⁴ gives m ≈ 3.6 × 10¹⁰ bits (4.3 GB) and k = 13.

Bit array ( bits, all zero to start)

0   1   being set   probe hit (bit is 1)   probe miss (bit is 0)

Each password → SHA-1 → k positions

h1 = first 8 bytes of SHA-1   h2 = next 8 bytes | 1   posi = (h1 + i·h2) mod 2⁶⁴ mod m,   i = 0 … k−1

Stage 2 — use the filter as a validator

Type a candidate password. The validator hashes it, computes the same k positions and reads those bits. The first 0 bit proves the password was never inserted, so the check stops there. If all k bits are 1 the password is probably in the corpus and is rejected.

    Why this is safe to use as a blocklist

    • No false negatives. A breached password always sets its k bits, so it can never slip through. That is what NIST's blocklist rule needs.
    • Rare, cheap false positives. Roughly p of never-seen passwords collide with set bits and are rejected; the user just picks another one. Production uses p = 1 in 10,000.
    • No password or hash leaves the server. Only ~13 reads into a memory-mapped file per check, in microseconds.
    • Size is fixed at build time. ~4.3 GB holds the whole 75 GB corpus; the file is rebuilt monthly and swapped atomically.
